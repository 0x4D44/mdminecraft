# Comprehensive Code Review
Date: 2026-01-08
Reviewer: Codex

**Scope**
Full repository review per `wrk_docs/2026.01.08 - CR - Code Review Plan.md`, covering `src/`, `crates/`, `tests/`, `tools/`, configs, and shaders. Generated code/artefacts (`target/`, `video_insights/`, `.venv/`, `wrk_docs/`, `wrk_journals/`) were excluded from the code inventory.

---

**Findings (ordered by severity)**

**High**
- **Multiplayer handshake never completes (client will hang or fail).**
  `MultiplayerServer::handle_new_client` validates the client handshake but never sends a `HandshakeResponse`. The client expects a response in `ClientConnection::handshake`, so connections stall. Fix by calling `ServerConnection::accept_handshake_with_entity(player_entity_id)` after a successful `accept_handshake`, or send an explicit rejection on failure. Files: `crates/server/src/multiplayer.rs`, `crates/net/src/connection.rs`, `crates/client/src/multiplayer.rs`.

**Medium**
- **TLS server-name validation hard-coded to `localhost`.**
  `ClientEndpoint::connect` always passes "localhost" as the server name for TLS verification. This breaks secure connections to non-localhost servers and pushes users toward `MDM_INSECURE_TLS=1`. Expose a hostname parameter or derive it from user input. File: `crates/net/src/transport.rs`.
- **World save writes are non-atomic (risk of corruption on crash/power loss).**
  `write_region` and `write_world_blob` write directly to the final path with `File::create` and no temp file + rename or `sync_all`. A mid-write crash can corrupt region/world blobs. Consider write-to-temp + `fsync` + atomic rename. Files: `crates/world/src/persist.rs`.

**Low**
- **Disconnected clients are never pruned.**
  `MultiplayerServer::tick` logs send failures but keeps the client entry. Over time this can accumulate dead clients and repeated warnings. Consider removing the client on send errors or after a timeout. File: `crates/server/src/multiplayer.rs`.
- **Reliable message delivery opens a new QUIC stream per message.**
  `ChannelManager::send_reliable` opens a unidirectional stream for every message. Under heavy load this can hit stream limits or add overhead. Consider stream reuse or batching for chat/diagnostics. File: `crates/net/src/channel.rs`.

**Architecture & Boundary Review (summary)**
- **Core primitives** live in `crates/core` (tick, registry keys, item types, deterministic RNG helper).
- **Simulation loop** is centralized in `src/game.rs` using `mdminecraft_world` and `mdminecraft_ecs` schedules.
- **Networking** uses QUIC via `quinn` with a typed protocol + schema hash (`crates/net`).
- **Rendering** is wgpu-based (`crates/render`) with headless support and UI overlay (`crates/ui3d`).
- **Automation** and headless execution are implemented in `src/automation/*` and `src/headless.rs`.
- **Persistence** is in `crates/world/src/persist.rs` with zstd + CRC headers.

---

**Module Notes (high-level review highlights)**
- `src/main.rs` and `src/headless.rs` cleanly split headless vs interactive execution paths. CLI validation is consistent and conservative.
- `crates/net` is structured with clear separation (transport, channels, codec, protocol, prediction, replay). Schema hash checking is in place.
- `crates/server`/`crates/client` currently provide thin multiplayer scaffolding. The handshake issue (above) blocks real use.
- `crates/world` is large but generally deterministic (seeded RNGs); uses CRC/zstd in persistence.
- `crates/render` and `crates/ui3d` provide a modern render pipeline with headless tests and shader validation.
- `crates/audio` uses a rodio backend when available and degrades gracefully to a stub.

---

**Cross‑Cutting Review Checklist**
- **Determinism:** Simulation RNGs are seeded from world/tick domains; no `thread_rng` in world systems. Non-deterministic wall-clock usage is primarily for UI/render or logging (`src/game.rs`, `src/commentary.rs`). Default world seed can be random when not supplied (intentional but non-reproducible unless logged).
- **Correctness & Safety:** Few panics in production paths; most `unwrap/expect` are within tests. The persistence write path is the primary durability risk.
- **Networking & Security:** TLS defaults to secure; `MDM_INSECURE_TLS=1` is clearly warned. Hard-coded SNI is the main blocker for real certificates.
- **Performance:** Chunk streaming has basic bandwidth limits; reliable channels open per-message streams which may be costly at scale.
- **Observability:** Logging uses `tracing` in core flows; automation logs are JSONL with flush per line.

---

**Tests & Coverage Gaps**
- Tests are concentrated in `crates/world/tests/*` (20 files), plus root integration tests for headless automation (`tests/*`). `crates/net/tests/proptest_codec_fuzz.rs` and `crates/render/tests/wgsl_validation.rs` cover protocol/shaders.
- **Gaps:**
  - No end-to-end client/server handshake integration test exercising `MultiplayerServer::handle_new_client`.
  - No persistence crash-safety test (atomic rename/partial write scenario).
  - No TLS hostname/SNI coverage for secure remote connections.

---

**Recommendations**
1) Fix multiplayer handshake response in `crates/server/src/multiplayer.rs` and add a simple integration test that validates client handshake completion.
2) Add a server-name parameter to `ClientEndpoint::connect` (or accept a hostname alongside `SocketAddr`) to support proper TLS verification. Include a unit test that verifies SNI propagation.
3) Make persistence writes atomic (temp file + rename + `sync_all`) and add a durability test where a partial write is simulated or validated.
4) Consider client pruning on send failure in `MultiplayerServer` to avoid stale connections.
5) For high-throughput reliable messaging, consider stream reuse or batching to avoid QUIC stream exhaustion.
